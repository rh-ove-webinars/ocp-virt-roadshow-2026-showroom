= Automating VMs with Ansible Automation Platform

== Introduction

So far in this roadshow we have managed virtual machines directly through the OpenShift web console. In the real world, administrators managing fleets of virtual machines -- whether ten or ten thousand -- need to automate repetitive day-2 tasks like patching, configuration changes, and compliance checks rather than clicking through them one at a time.

Red Hat Ansible Automation Platform (AAP) is designed for exactly this. In this module we will build, by hand, the same kind of automation pipeline you would set up in a real environment: a Project pointing at a Git repository, a dynamic Inventory that discovers OpenShift Virtualization VMs automatically, and a Job Template that runs a playbook against whatever it finds. We will then create a brand new virtual machine, point our new automation at it, and watch AAP patch it for us.

.*Goals*

* Create a virtual machine pre-configured for Ansible access using cloud-init
* Create an AAP Project backed by a Git repository
* Create a dynamic AAP Inventory that discovers OpenShift Virtualization VMs using OpenShift credentials
* Review the pre-built playbook that will patch your VM
* Create and launch a Job Template
* Verify the automation actually changed your VM

NOTE: Your Ansible Automation Platform Organization and user have already been created for you by your workshop facilitator, along with two Credentials -- *VM SSH Key* and *OpenShift Access* -- so that you don't have to paste any private keys or API tokens by hand. Everything else in this module, you will build yourself.

[[create_vm]]
== Create a Virtual Machine for This Exercise

We need a virtual machine for Ansible to manage. This time, instead of a quick-create, we will customize the VM's cloud-init configuration so that our AAP credential's SSH key is authorized on first boot.

. Since this VM will take a couple of minutes to boot and become discoverable, let's start it now and come back to configuring AAP while it finishes.

. In the OpenShift console, switch to the *Virtualization* perspective, and select your *vmexamples-{user}* project.

. Click *Create VirtualMachine*, select *From template*, and choose the *Fedora VM* tile as you did in Module 1. This time, click *Customize VirtualMachine* instead of *Quick create VirtualMachine*.
+
// TODO: screenshot - Customize VirtualMachine button on the Fedora tile

. Set the name to *ansible-demo* and continue to the customization screen.
+
// TODO: screenshot - naming the VM ansible-demo

. Click on the *Scripts* tab, and in the *Cloud-init* section click *Edit*.
+
// TODO: screenshot - Scripts tab, Cloud-init Edit button

. Choose *Configure via: Script*, and replace the contents with the following, which authorizes the AAP-managed SSH key for the default *fedora* user on first boot:
+
[source,yaml,role=execute,subs="attributes+"]
----
userData: |-
  #cloud-config
  user: fedora
  password: ${CLOUD_USER_PASSWORD}
  chpasswd: { expire: False }
  ssh_authorized_keys:
    - {aap_ssh_pubkey}
----
+
// TODO: screenshot - cloud-init script with ssh_authorized_keys

. Click *Save*, then click *Create VirtualMachine*.
+
// TODO: screenshot - Create VirtualMachine button

[[view_playbook]]
== Take a Look at the Playbook

Before we run any automation blindly, let's actually read what it does.

. Open the playbook directly on GitHub:
+
https://github.com/rh-ove-webinars/ocp-virt-roadshow-2026-showroom/blob/main/automation/vm-content/playbooks/patch-vm.yml[View patch-vm.yml on GitHub^]

. Notice what it does, step by step:
+
* Updates all packages on the target host with `dnf`
* Checks whether the update requires a reboot
* Reboots the VM and waits for it to come back online, only if needed
* Writes a line into `/etc/motd` recording that it was patched by Ansible Automation Platform, along with a timestamp and the running kernel version
* Prints a short summary of what changed
+
This is a deliberately simple example of a patch-management playbook -- the same pattern (update, conditionally reboot, verify, report) is exactly what you would build on for a real fleet of VMs, just against a much larger inventory.

[[verify]]
== Verify the Patch

Let's go back to the OpenShift console and confirm the change actually happened on the virtual machine.

. In the OpenShift console, open the *Console* tab for the *ansible-demo* VM and log in using the *fedora* user and the guest credentials shown, as you have done in earlier modules.

. Run the following command to see the banner Ansible left behind:
+
[source,sh,role=execute]
----
cat /etc/motd
----
+
You should see a line similar to:
+
[source,text]
----
Patched by Ansible Automation Platform on 2026-09-18T14:32:01Z (kernel 6.11.0-63.fc41.x86_64)
----
+
// TODO: screenshot - motd output showing the patch banner

. This confirms that Ansible Automation Platform connected to your virtual machine, applied updates, and (if a reboot was needed) rebooted it -- using automation you configured yourself in this module, from a dynamically discovered inventory, end to end.

== Summary

In this module we built an Ansible Automation Platform automation pipeline by hand: a Project synced from Git, a dynamic Inventory that discovers OpenShift Virtualization VMs using our own OpenShift credentials, and a Job Template that ties a pre-built patch-management playbook to that inventory. We created a new virtual machine configured via cloud-init to accept AAP's SSH key, watched AAP discover it automatically, and launched a real patch against it -- leaving a verifiable record of the change on the VM itself. This same pattern -- Project, Inventory, Job Template -- scales from the one VM we patched here to fleets of hundreds or thousands of virtual machines managed the same way.
