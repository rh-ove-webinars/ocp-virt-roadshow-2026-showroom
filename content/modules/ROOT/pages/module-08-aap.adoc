= Automating VMs with Ansible Automation Platform

== Introduction

So far in this roadshow we have managed virtual machines directly through the OpenShift web console. In the real world, administrators managing fleets of virtual machines -- whether ten or ten thousand -- need to automate repetitive day-2 tasks like patching, configuration changes, and compliance checks rather than clicking through them one at a time.

Red Hat Ansible Automation Platform (AAP) is designed for exactly this. In this module we will see how Ansible Automation Platform and OpenShift Virtualization work together: AAP can dynamically *discover* virtual machines running in OpenShift Virtualization as Ansible inventory, and then run playbooks against them just like it would against any other Linux host.

We are going to demonstrate this with a simple patch management scenario: we will point AAP at the *fedora01* virtual machine created back in Module 1, let AAP discover it automatically, and run a pre-built playbook that updates its packages, reboots it if needed, and leaves a visible record of the change on the VM itself.

.*Goals*

* Understand how Ansible Automation Platform connects to OpenShift Virtualization
* Authorize AAP to manage your virtual machine over SSH
* Discover your virtual machine dynamically as AAP inventory
* Run a pre-built playbook to patch and verify your virtual machine

NOTE: Your Ansible Automation Platform organization, user, and the demo Project/Inventory/Job Template used in this module have already been created for you by your workshop facilitator -- you do not need to build any of this from scratch, only use it.

. With *fedora01* selected, click on the *Configuration* tab, then the *SSH* subtab.
+

----

----
+

. Within a few moments the key is injected into the *fedora* user's `authorized_keys` on the running VM -- no reboot required. This is the same mechanism you would use in production to let Ansible Automation Platform (or any other automation) manage a fleet of running VMs without disrupting them.

[[verify]]
== Verify the Patch

Let's go back to the OpenShift console and confirm the change actually happened on the virtual machine.

. In the OpenShift console, open the *Console* tab for the *fedora01* VM and log in using the guest credentials shown, as you have done in earlier modules.

. Run the following command to see the banner Ansible left behind:
+
[source,sh,role=execute]
----
cat /etc/motd
----
+
You should see a line similar to:
+
[source,text]
----
Patched by Ansible Automation Platform on 2026-09-18T14:32:01Z (kernel 6.11.0-63.fc41.x86_64)
----
+

. This confirms that Ansible Automation Platform connected to your virtual machine, applied updates, and (if a reboot was needed) rebooted it -- all triggered by a single click of the *Launch* button, against a host it discovered automatically.

== Summary

In this module we connected Ansible Automation Platform to OpenShift Virtualization and used it to automate a common day-2 operations task: patch management. We saw how AAP can dynamically discover virtual machines running in OpenShift as inventory, how OpenShift Virtualization's SSH key injection lets automation reach a running VM without disrupting it, and how a single pre-built playbook and Job Template can apply updates, handle a reboot, and leave a verifiable record of the change -- all without an administrator needing to log into the VM by hand. This same pattern scales from the one VM we patched here to fleets of hundreds or thousands of virtual machines managed the same way.
