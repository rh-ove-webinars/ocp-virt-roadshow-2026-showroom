== Introduction

Once a virtual machine has been created, most of the work of keeping it healthy is repetitive: applying patches, rebooting when a new kernel arrives, adjusting configuration, and proving afterwards that it actually happened. Doing that by hand, one VM at a time in the console, does not scale past a handful of machines, and it is exactly the kind of day-2 work that administrators of large virtual environments automate.

https://www.redhat.com/en/technologies/management/ansible[*Red Hat Ansible Automation Platform*^] (AAP) is Red Hat's enterprise automation platform. It runs Ansible playbooks against sets of hosts, stores the credentials needed to reach them, and gives teams a shared place to build, launch and audit that automation. Because OpenShift Virtualization virtual machines are described by the same Kubernetes API as everything else in the cluster, AAP can also discover them automatically, so the list of machines to automate never has to be maintained by hand.

In this portion of the lab, we will build a small automation pipeline in AAP ourselves and use it to patch a virtual machine. You will create a new virtual machine, then in AAP you will create a *Project* that holds the playbook, a dynamic *Inventory* that discovers the VM, and a *Job Template* that ties them together, and finally launch it.

.*Goals*

* Create a virtual machine that is ready to be managed by Ansible using cloud-init
* Create an AAP Project that pulls a playbook from a Git repository
* Review the playbook that will patch the virtual machine
* Create a dynamic Inventory that discovers OpenShift Virtualization VMs using OpenShift credentials
* Create and launch a Job Template
* Verify that the automation changed the virtual machine

NOTE: Your AAP organization and user, along with two credentials named *VM SSH Key* and *OpenShift Access*, have already been created for you, so that you do not have to copy private keys or API tokens by hand. Everything else in this module you will build yourself.

[[view_playbook]]
== Take a Look at the Playbook

Before running any automation, it is worth reading what it will do to your machines. The repository your Project just synchronized contains a playbook called *patch-vm.yml*, which is shown below in full.

[source,yaml]
----
---
# Pre-built demo playbook used by the "Automating VMs with Ansible Automation Platform"
# module of the lab guide.
# Tasks : update packages, reboot if the kernel changed, confirm the VM comes
# back up, and leave visible proof of the change in /etc/motd.
- name: Patch management demo - OpenShift Virtualization VM
  hosts: all
  become: true
  gather_facts: true

  vars:
    ansible_ssh_use_tty: false

  tasks:
    - name: Update all packages
      ansible.builtin.dnf:
        name: "*"
        state: latest
      register: dnf_update

    - name: Check whether a reboot is required
      ansible.builtin.command: dnf needs-restarting -r
      register: needs_restart
      changed_when: false
      failed_when: needs_restart.rc not in [0, 1]

    - name: Reboot the VM if a newer kernel/library requires it
      ansible.builtin.reboot:
        reboot_timeout: 300
      when: needs_restart.rc == 1

    - name: Wait for the VM to come back and accept connections
      ansible.builtin.wait_for_connection:
        delay: 10
        timeout: 300
      when: needs_restart.rc == 1

    - name: Re-gather facts after the reboot
      ansible.builtin.setup:
      when: needs_restart.rc == 1

    - name: Record a patch banner in /etc/motd as visible proof of the change
      ansible.builtin.lineinfile:
        path: /etc/motd
        regexp: '^Patched by Ansible Automation Platform'
        line: "Patched by Ansible Automation Platform on {{ ansible_date_time.iso8601 }} (kernel {{ ansible_kernel }})"
        create: true

    - name: Show a summary of what changed
      ansible.builtin.debug:
        msg:
          - "Host: {{ inventory_hostname }}"
          - "Packages updated: {{ dnf_update.changed }}"
          - "Reboot performed: {{ needs_restart.rc == 1 }}"
          - "Kernel now running: {{ ansible_kernel }}"
----

Notice the following about how the playbook is put together:

* *hosts: all* means the playbook runs against every host in whichever inventory it is launched with. We will launch it against an inventory that contains only our virtual machine.
* *become: true* tells Ansible to run the tasks with administrative privileges (using `sudo`), which package updates and writing to `/etc` require.
* *vars* sets a variable for the whole play. Here *ansible_ssh_use_tty* tells Ansible not to allocate a terminal for the tasks in this play.
* Each entry under *tasks* uses an Ansible module to describe a desired outcome rather than a script of commands: *dnf* updates the packages, *reboot* restarts the machine and waits for it to return, and *lineinfile* makes sure a line is present in a file, replacing any existing line that matches instead of adding another.
* Some tasks only run *when* a condition is true. The playbook asks `dnf needs-restarting -r` whether the update requires a reboot and only reboots the virtual machine if it does.
* Finally, the playbook writes a line to `/etc/motd` containing the date and the running kernel version. This leaves a visible record on the machine, which we will look for at the end of the module. Because the task replaces its own line from any earlier run, running the job again updates the banner instead of adding a second one.

This is a deliberately simple example, but the pattern of updating, conditionally rebooting, verifying and reporting is the same one that is used to patch a fleet of hundreds of machines. Only the size of the inventory changes.

== Create a Dynamic Inventory Using OpenShift Credentials

An AAP *Inventory* is the list of hosts that automation runs against. Rather than typing in the name and address of our virtual machine by hand, we will have AAP discover it from the OpenShift Virtualization API, so that the inventory stays correct as virtual machines come and go.

. Click on *Automation Execution* in the left-side menu, then *Infrastructure*, then *Inventories*, and click on the *Create inventory* button and select *Create inventory*.
+
image::2026_summer/module-08-aap/14_AAP_Inventory_init.png[link=self, window=blank, width=100%]

. Fill in the following values, and when finished click on the *Create inventory* button.
+
* *Name:* My VMs
* *Organization:* {user}
+
image::2026_summer/module-08-aap/15_AAP_Inventory.png[link=self, window=blank, width=100%]

. On the inventory that was just created, click on the *Sources* tab and then the *Create source* button.
+
image::2026_summer/module-08-aap/16_AAP_Inventory_Source_init.png[link=self, window=blank, width=100%]

. Fill in the following values, and leave all of the other settings at their defaults:
+
* *Name:* OpenShift Virtualization VMs
* *Source:* Supported OpenShift Virtualization
* *Credential:* OpenShift Access
* *Source variables:* add the following, which limits the discovery to your own project:
+
[source,yaml,role=execute,subs="attributes+"]
----
namespaces:
  - vmexamples-{user}
----
+
The *Supported OpenShift Virtualization* source type is built in to AAP and supported by Red Hat. It uses the *OpenShift Access* credential to query the OpenShift API and turns virtual machines into Ansible hosts, with no inventory file to maintain. Since it uses your credential, it can only ever see the virtual machines that your own OpenShift user can see.
+
NOTE: Without the source variables above, AAP would discover every virtual machine that your user can see, which includes the three stopped virtual machines that were staged for you in the *vmimported-{user}* project. The playbook would then try, and fail, to patch them as well.
+
image::2026_summer/module-08-aap/17_AAP_Inventory_Source.png[link=self, window=blank, width=100%]

. Click on the *Create source* button to save it. AAP opens the *Details* page of the new source.

Now let's confirm that the change was actually made on the virtual machine.

. In the OpenShift console, click on the *ansible-demo* virtual machine, then the *Console* tab, and use the *Guest login credentials* that are provided, along with the *Copy* and *Paste to console* buttons, to log in as the *fedora* user.

image::2026_summer/module-08-aap/26_VM_Console.png[link=self, window=blank, width=100%]

+

----
+
The banner is also displayed automatically when you log in, because the contents of `/etc/motd` are shown at every login. You should see a line similar to the following:
+
[source,text]
----
Patched by Ansible Automation Platform on 2026-09-21T13:53:48Z (kernel 7.2.5-200.fc44.x86_64)

This confirms that AAP logged in to the virtual machine, applied the updates, rebooted it, and recorded the result, all from a job that you configured and launched yourself.

== Summary

In this section of our lab we used Red Hat Ansible Automation Platform together with OpenShift Virtualization to automate a common day-2 task. We created a virtual machine configured with cloud-init to trust AAP's SSH key, then built a Project that pulls a playbook from Git, a dynamic Inventory that discovers the virtual machine from the OpenShift Virtualization API, and a Job Template that ties them together. Launching it patched the virtual machine, rebooted it, and left a verifiable record of the change.

The same Project, Inventory and Job Template pattern scales from the single virtual machine used here to very large environments, and the playbook can be extended to perform any other task that you would otherwise do by hand. To learn more about the platform, please see the https://docs.redhat.com/en/documentation/red_hat_ansible_automation_platform/2.7[Red Hat Ansible Automation Platform documentation^], or ask the proctors for the workshop.
